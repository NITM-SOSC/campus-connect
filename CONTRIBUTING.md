# Contributing to Campus Connect

Thank you for considering a contribution. Campus Connect is an early-stage initiative: thoughtful questions, documentation improvements, and constructive proposals are valuable alongside code.

## Before you start

1. Read the [README](README.md), [architecture proposal](docs/ARCHITECTURE.md), [roadmap](docs/ROADMAP.md), and [Code of Conduct](CODE_OF_CONDUCT.md).
2. Search existing issues and pull requests before opening a new one.
3. For a substantial or potentially disruptive feature, open an issue first so the community can discuss scope. Proposed capabilities are not commitments or existing functionality.
4. Do not include credentials, private student data, or sensitive security details in public issues or pull requests.

## Contribution workflow

1. **Create an issue or discussion.** Describe the problem, context, and intended outcome. Use the supplied issue form appropriate to the report. Feature discussions should clarify the need before prescribing a technical solution.
2. **Agree on scope.** Maintainers and contributors can refine the proposal and identify dependencies. Assignment or discussion is not a guarantee of acceptance or delivery.
3. **Work on a branch.** Fork the repository, create a focused branch, and keep changes scoped. Use descriptive names, for example `docs/clarify-contribution-flow` or `feat/event-planning-proposal`.
4. **Submit a pull request.** Target `main` unless maintainers specify otherwise. Link the related issue, explain the change, and complete the pull request template.
5. **Test and document.** Run relevant checks and describe what you did. For documentation-only changes, proofread rendered Markdown and verify relative links.
6. **Participate in review.** Respond constructively to feedback and update the branch as needed. Review is collaborative and may request changes.
7. **Maintainer approval and merge.** Only maintainers merge accepted contributions. A pull request is not complete until it has the required review and is merged.

## Development expectations

- Keep changes clear, focused, and accessible to readers new to the project.
- Clearly label proposals as proposals; do not imply planned or implemented functionality without evidence.
- Avoid introducing a framework, dependency, infrastructure, or stack choice without prior discussion and agreement.
- Do not add real credentials, secrets, or personally identifying information.
- Follow existing conventions and update relevant documentation when behavior or project guidance changes.
- Be respectful, assume good intent, and follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Checks

This repository currently has no application code, dependency manifest, or automated test suite. For documentation changes, check spelling, heading structure, Markdown rendering, and local links. For future code contributions, include the appropriate test commands and results in your pull request; project-specific checks will be documented when established.

## Suggested labels

Maintainers may use labels to help contributors find work:

- `good first issue` — scoped tasks suitable for someone new to the project.
- `help wanted` — tasks where additional contributors are welcome.
- `documentation` — documentation and writing improvements.
- `frontend` and `backend` — application-area labels once those areas exist.
- `enhancement` — proposed or accepted improvements.
- `bug` — verified defects in implemented functionality.
- `security` — security-related tracking; do not use a public issue to disclose an unpatched vulnerability.

Labels are recommendations; maintainers can adapt them to the repository's needs.
